# Token预算

## 一句话定义

在固定或可变上下文长度下，**显式分配**各块内容（系统、记忆、检索、工具、用户）的 token 上限，避免关键指令被挤出。

## 先理解什么（入门）

模型能看的 token 有上限；费用也常按 token 计。没有预算意识时，团队会习惯性「多塞一点检索结果」，最后发现**系统安全约束被截断**。

## 再理解什么（进阶）

- **硬预算 vs 软预算**：硬预算由代码裁剪；软预算由模型自摘要（有风险）。
- **优先级队列**：系统 > 安全 > 当前任务 > 历史闲聊 > 可丢弃的示例。
- **动态压缩**：对旧轮对话做摘要再保留，而不是全删或全留。

## 落地要点（实践）

- 在配置里写明每类上限，并在日志里打实际占比。
- 超长工具输出走「摘要 + 原始落盘」，需要时再拉全量。
- 上线前用真实会话做压力测试，观察截断点。

## 常见坑

- 只优化 prompt 长度，不优化检索 chunk 大小。
- 多模态 token 计算与纯文本不同，预算表未区分。
